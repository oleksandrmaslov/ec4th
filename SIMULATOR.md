# Running ec4th under simavr

This runs the Arduino Nano image on your machine, with a real Forth prompt on
the simulated serial port. No board required.

## 1. Install the prerequisites

The cross build needs `gforth` and `avr-objcopy`; the simulator needs simavr's
runtime *and* its development files, because the front end in `tools/sim/` is a
small C program linked against `libsimavr`:

```bash
sudo apt-get install gforth binutils-avr simavr libsimavr-dev gdb-avr
```

`libsimavr-dev` is the one that is easy to miss. Installing plain `simavr` gives
you the `simavr` command but no headers, and `make sim` will stop with a message
telling you to install it.

## 2. Build and run

```bash
make sim
```

That does three things: cross-compiles the firmware with gforth, compiles the
simulator front end into `output/ec4th-sim`, and starts it. You get:

```
ec4th ok
```

Type at it exactly as you would over a serial line:

```
1 2 + . cr          →  3
: sq dup * ;        →  compiled
9 sq .              →  81
```

Quit with **Ctrl-C**. `./run.sh` does the same thing.

## 3. Feeding it a source file

Because input comes from stdin, whole files can be piped in. This is the
simulator equivalent of pasting into `tio`:

```bash
make                                    # build the firmware once
output/ec4th-sim output/ec4th-arduino-nano-regular.bin < ../forth.fs
```

or a file plus some words to exercise it:

```bash
{ cat ../forth.fs; echo '77 11 and dup .BIN8-SHORT .'; } \
  | output/ec4th-sim output/ec4th-arduino-nano-regular.bin
```

When stdin reaches end of file the simulator waits until the board has been
quiet for 200 ms and then exits, so this works in scripts and test runs. Use
`-q <ms>` if a definition needs longer to settle.

### Why there is no `-o 1` here

On real hardware the README tells you to run `tio -b 115200 -o 1`, because ec4th
drops characters when a file arrives faster than it compiles. That delay is not
needed under the simulator. `ec4th-sim` watches the XOFF (`$13`) and XON (`$11`)
bytes that the receive ISR in `+/ec4th/target/avr/usart-ringbuffer.fs` sends
when its ring buffer fills, and holds off the sender until ec4th asks for more.
Files paste in losslessly at full speed. `-d <ms>` is still there if you want to
reproduce a slow terminal deliberately, and `-X` shows the flow control bytes
instead of acting on them.

## 4. Debugging with avr-gdb

```bash
make debug
```

This builds `output/ec4th-arduino-nano-regular.elf`, starts the simulator halted
at reset, and waits for a debugger. In another terminal:

```bash
avr-gdb output/ec4th-arduino-nano-regular.elf \
  -x tools/sim/ec4th-gdb.py -ex 'target remote :1234'
```

The ELF is generated by `tools/sim/mkelf.py` from the flash image plus the
symbol table that `build.fs` writes, so all 407 Forth words are available to gdb
by name — including awkward ones like `0=` and `u<=`:

```
(gdb) info symbol 0x2e2
dup in section .text
```

### Where to put a breakpoint

Two details about the memory layout will otherwise waste your afternoon.

**ROM addresses are offset by `$8000`.** The cross compiler places the ROM
dictionary at `$8000` in the Forth address space (the `rom-dictionary` region in
`build.fs`) while flash starts at zero, so a word listed at `$82E2` in the `.sym`
file lives at `0x2e2` in gdb. `mkelf.py` has already applied that shift; it
matters only when you read a raw address out of the `.sym` file yourself.

**A symbol points at the word's code field, not at its code.** Each dictionary
entry starts with a two-byte code field, then two filler bytes, then the body.
So for a primitive, the machine code begins at *symbol + 4*:

```
(gdb) break *(dup+4)
Breakpoint 1 at 0x2e6
(gdb) continue

Breakpoint 1, 0x000002e6 in dup ()
(gdb) x/3i $pc
=> 0x2e6 <dup+4>:	st	Y+, r24
   0x2e8 <dup+6>:	st	Y+, r25
   0x2ea <dup+8>:	rjmp	.-452
```

`break *dup` sets a breakpoint on the code field itself, which is data the inner
interpreter reads and the PC never reaches — it will simply never fire.

For the same reason, **colon definitions cannot be breakpointed at all** by
address. A word like `boot` is a list of addresses, not instructions; its code
field points at `:docol` and the thread that follows is data. To catch colon
words being entered, break on the inner interpreter instead:

```
(gdb) break *':docol'        # every colon word entry
```

The four `:`-prefixed symbols (`:docol`, `:dovar`, `:docon`, `:dodoes`) are
assembler labels rather than dictionary entries, so those *are* real machine
code at the address given, with no `+4`.

### The helper commands

Forth word names and gdb's C expression parser do not get along. `:docol` needs
quoting, and two-character names like `0=` are rejected outright as invalid
character constants — `break *('0='+4)` cannot be written at all.

`tools/sim/ec4th-gdb.py` sidesteps that by reading the `.sym` file directly. It
finds `output/*.sym` by itself and applies both offsets for you:

| command | what it does |
| --- | --- |
| `fbreak <word>` | break on the word's machine code (`+4` unless it is a `:` label) |
| `faddr <word>` | show its code field and body addresses |
| `fsym [expr]` | name the word an address falls in, default `$pc` |
| `fsymfile <path>` | read a different `.sym` file |

```
(gdb) fbreak 0=
breakpoint on 0= at 0x422
(gdb) continue

Breakpoint 1, 0x00000422 in 0= ()
(gdb) fsym
0x422: 0= + 4
```

`fsym` is the useful one when something has crashed: it answers "which word am I
in" for any address, which plain `info symbol` only does for names gdb can
already parse.

## 5. Attaching a terminal program instead

If you would rather drive the simulator with the same tool you use on hardware:

```bash
output/ec4th-sim -p output/ec4th-arduino-nano-regular.bin
```

It reports the pty it created and also points a stable symlink at it, so from
another terminal:

```
uart_pty_init bridge on port *** /dev/pts/5 ***
uart_pty_connect: /tmp/simavr-uart0 now points to /dev/pts/5
```

```bash
tio -o 1 /tmp/simavr-uart0
```

In this mode ec4th-sim does not intercept the flow control bytes, so keep tio's
`-o 1` exactly as you would with a real board.

## 6. What the simulator does and does not model

* USART0, timers and interrupts are simulated, which covers everything ec4th
  currently uses. The `~4ms` figures ec4th prints are simulated time and are
  meaningful.
* The simulation is not throttled to real time; it runs as fast as your machine
  allows, so a long compile finishes sooner than on the board.
* Nothing is attached to the GPIO pins. Words that toggle pins will run, but
  there is no LED to watch. simavr can drive pins from a `.vcd` input file if
  you ever need that.
* `output/ec4th-sim` is a host binary. `make clean` removes it along with
  everything else in `output/`.

## 7. Troubleshooting

**`make sim` stops with "Could not build output/ec4th-sim"** — `libsimavr-dev`
is missing, or `pkg-config --cflags simavr` returns nothing. Install it, or
point the build at your own copy:

```bash
make sim SIM_CFLAGS="-I/path/to/include/simavr" \
         SIM_LIBS="/path/to/libsimavrparts.a -lsimavr -lpthread -lutil"
```

**The banner appears but typing does nothing** — check you are running
`output/ec4th-sim` and not the stock `simavr` command. The stock tool copies
UART output to the console but never feeds anything into the receiver, so it can
only ever show you the banner.

**The first characters of a pasted file go missing** — that is what the wait for
the boot banner prevents; it is disabled by `-W`. Without it, input sent while
the firmware is still in its reset code, before it has set `RXEN`, is lost.
